# 短信验证码登录与找回密码设计

日期：2026-08-18  
状态：已获用户批准，待实施计划

## 1. 背景与目标

系统当前支持手机号加密码登录、邮箱链接找回密码，并已存在一套尚未在线启用的短信验证码找回密码代码。阿里云短信签名 `温州市少航科创中心` 已通过审核，但运营商报备仍在进行，线上服务器也尚未配置短信 AccessKey、签名和模板代码。

本次升级目标：

1. 保留已上线的邮箱链接找回密码。
2. 新增“已注册手机号 + 短信验证码”免密码登录。
3. 完成手机号短信验证码找回密码。
4. 登录验证码与找回验证码采用两个独立阿里云短信模板。
5. 预留阿里云验证码 2.0 人机验证，默认关闭，后续通过配置开启。
6. 在运营商报备和短信模板尚未完全就绪时，先完成代码和自动化验证，但不向线上用户开放短信入口。

## 2. 非目标

本次不实现：

- 未注册手机号通过短信自动注册。
- 短信通知报名、审核、成绩或证书结果。
- 短信营销或群发。
- 更换现有会话、角色或组织审核体系。
- 当前阶段启用或购买阿里云验证码 2.0。
- 使用短信登录绕过管理员设置的强制修改密码状态。

## 3. 用户与账户规则

短信登录仅服务于系统中已经存在、状态正常启用的账号，包括普通用户、组织负责人和平台管理员。

- 未注册手机号不创建账号。
- 待审核、已驳回或已停用的组织账号不能通过短信登录。
- 已停用的普通用户或管理员账号不能通过短信登录。
- `mustChangePassword` 状态继续生效；短信登录成功后仍须先完成修改密码。
- 短信登录不修改、清空或替换用户现有密码。
- 短信找回成功后更新密码、递增会话版本、清除临时密码状态，并使旧会话失效，与现有邮箱找回逻辑保持一致。

为避免手机号枚举，发送接口对已注册和未注册手机号返回相同文案：

> 如果该手机号已注册，验证码将发送到该号码。

未注册或不可登录的手机号不会实际发送短信。页面同时提供“没有账号？去注册”的普通引导。

## 4. 方案选择

采用“共享验证码安全底层、按用途隔离”的方案。

### 4.1 选择理由

- 复用手机号规范化、验证码生成、摘要存储、有效期、限流和错误次数逻辑。
- 登录与找回各自拥有独立用途、模板和挑战状态，避免互相覆盖或混用。
- 密码登录和短信登录共用会话创建逻辑，避免角色和强制改密行为分叉。
- 不引入第三方统一身份平台，不迁移现有用户数据。

### 4.2 用途命名

- `sms-login`：短信验证码登录。
- `sms-password-reset`：短信验证码找回密码。

验证码摘要必须包含用途和手机号；一个用途生成的验证码不能用于另一个用途。

## 5. 页面与交互

### 5.1 登录页

登录区域提供两个切换项：

- 密码登录：保持现有手机号和密码表单。
- 短信验证码登录：手机号、获取验证码按钮、6 位验证码输入框和登录按钮。

发送成功后：

- 显示统一安全提示。
- 获取按钮进入 60 秒倒计时。
- 验证码输入框仅接受 6 位数字。
- 提示验证码 5 分钟内有效。
- 页面刷新后不保留验证码；可以保留用户已经输入的手机号。

短信功能配置不完整时，不显示短信登录切换项。

### 5.2 找回密码页

保留两个方式：

- 邮箱链接：保持现有流程。
- 手机验证码：输入注册手机号、获取验证码、填写验证码和新密码。

短信找回完成后返回登录页，并提示使用新密码登录。

短信功能配置不完整时不显示手机验证码方式，邮箱找回不受影响。

### 5.3 错误与状态提示

- 限流：`请求过于频繁，请稍后再试`。
- 校验失败：`验证码无效或已过期`。
- 账号状态在验证期间发生变化：使用统一的验证码无效提示，不能建立会话。
- 阿里云发送失败：不向用户暴露供应商响应、Request ID、AccessKey 或内部堆栈。
- 密码规则错误：继续使用现有密码校验提示。

## 6. API 设计

### 6.1 公开功能开关

`GET /api/public/features` 增加：

- `smsLoginEnabled`
- 保留 `smsPasswordResetEnabled`
- `captchaEnabled`

两个短信能力独立报告状态：AccessKey、签名和登录模板完整时启用短信登录；AccessKey、签名和找回模板完整时启用短信找回。一个模板仍在审核时，不影响另一个已经就绪的能力。

### 6.2 短信登录

`POST /api/auth/sms-login/request`

请求：

```json
{
  "phone": "13800000001",
  "captchaVerifyParam": "可选；验证码2.0启用后必填"
}
```

响应始终使用统一提示；限流或人机验证失败除外。

`POST /api/auth/sms-login/confirm`

请求：

```json
{
  "phone": "13800000001",
  "code": "123456"
}
```

成功响应与现有密码登录相同，返回公开用户信息和所属组织，并建立同等安全属性的会话。

### 6.3 短信找回密码

保留现有接口：

- `POST /api/auth/password-reset/sms/request`
- `POST /api/auth/password-reset/sms/confirm`

发送接口增加可选 `captchaVerifyParam`；验证码2.0启用后必填。

### 6.4 邮箱找回密码

保留现有接口和邮箱链接流程。发送接口预留 `captchaVerifyParam`；验证码2.0启用后必须通过后端复验才能发送邮件。

## 7. 验证码状态与安全

### 7.1 验证码规则

- 6 位数字。
- 5 分钟有效。
- 60 秒后才能重新发送。
- 每手机号每小时最多发送 5 次。
- 每 IP 每小时最多请求 20 次。
- 每个验证码最多错误尝试 5 次。
- 验证成功后立即失效，只能使用一次。
- 重新发送后，同手机号、同用途的旧验证码立即失效。
- 登录验证码和找回验证码互不影响。

### 7.2 存储要求

- 数据库或认证状态存储中只保存带服务器密钥的验证码摘要，不保存验证码明文。
- 摘要输入包含用途、规范化手机号和验证码。
- 挑战记录包含用途、手机号、摘要、过期时间和尝试次数。
- 发送失败只删除本次生成的具体挑战，不得按手机号或用途批量删除，以免旧发送失败误删后来生成的新验证码。
- 日志不得记录验证码、AccessKey、Secret 或完整供应商响应；手机号如需记录必须脱敏。

### 7.3 执行顺序

发送接口：

1. 规范化手机号。
2. 执行本地手机号和 IP 限流。
3. 验证码2.0启用时，调用后端适配器复验人机参数。
4. 读取账号并检查当前状态。
5. 为有效账号保存具体用途的挑战并异步发送对应模板短信。
6. 对有效和无效账号返回相同提示。

确认登录：

1. 验证并一次性消费 `sms-login` 挑战。
2. 在建立会话前重新读取账号，确认账号仍存在且启用。
3. 使用与密码登录相同的会话再生、会话版本和响应函数。
4. 保留短信发送频率记录；登录成功不能清零发送限额，避免通过反复成功登录绕过短信成本保护。

确认找回：

1. 先校验新密码规则。
2. 验证并一次性消费 `sms-password-reset` 挑战。
3. 在全局变更锁内重新读取用户并更新密码。
4. 递增 `sessionVersion`、清除临时密码和强制改密状态。

## 8. 阿里云短信适配

使用两个模板：

- 登录模板：明确说明验证码用于登录。
- 找回模板：明确说明验证码用于重置密码。

建议环境变量：

```dotenv
ALIBABA_CLOUD_ACCESS_KEY_ID=
ALIBABA_CLOUD_ACCESS_KEY_SECRET=
ALIYUN_SMS_SIGN_NAME=温州市少航科创中心
ALIYUN_SMS_LOGIN_TEMPLATE_CODE=
ALIYUN_SMS_RESET_TEMPLATE_CODE=
```

不再以单一模板代码同时承担两种用途。兼容迁移期间可以识别旧变量，但线上启用前必须完成两个新模板配置。

使用专用 RAM 子账号并遵循最小权限原则，不使用阿里云主账号长期 AccessKey。

## 9. 阿里云验证码 2.0 预留

本阶段完成适配但默认关闭：

```dotenv
ALIYUN_CAPTCHA_ENABLED=false
ALIYUN_CAPTCHA_LOGIN_SCENE_ID=
ALIYUN_CAPTCHA_SMS_RESET_SCENE_ID=
ALIYUN_CAPTCHA_EMAIL_RESET_SCENE_ID=
```

设计要求：

- 提供统一的人机验证前端组件和后端适配器。
- 关闭时不显示验证组件，发送接口继续由本地限流保护。
- 开启后，三个发送入口分别使用自己的场景 ID。
- 开启但配置不完整时必须失败关闭：拒绝相关发送，而不是跳过验证。
- 人机验证失败不生成验证码、不保存挑战、不发送短信或邮件。
- 后期开通服务时只需配置环境变量并重启服务，不修改业务代码。

## 10. 部署策略

分两阶段上线：

### 阶段一：代码就绪、功能关闭

- 完成短信登录、短信找回和验证码2.0预留代码。
- 运行 API、管理端测试和生产构建。
- 部署代码，但不配置短信 AccessKey 和模板代码。
- 线上仅保留现有密码登录和邮箱找回。

### 阶段二：短信正式启用

- 等登录和找回两个短信模板审核通过。
- 等运营商报备状态稳定。
- 配置专用 RAM AccessKey、签名和两个模板代码。
- 重启 API 并确认公开功能开关变为启用。
- 分别使用移动、联通、电信手机号验证登录和找回短信。
- 验证成功后向用户开放入口。

验证码2.0继续保持关闭；后期开通后再填写三个场景并启用开关。

## 11. 测试与验收

### 11.1 API 单元与集成测试

- 登录请求对已注册和未注册手机号响应一致。
- 未注册、待审核、驳回、停用账号不实际发送短信。
- 登录与找回使用不同模板和用途。
- 两类验证码不能交叉使用。
- 重发只撤销同一用途的旧挑战。
- 旧短信发送失败不能删除新挑战。
- 验证码只保存摘要。
- 5 分钟过期、5 次错误、60 秒冷却和小时上限生效。
- 短信登录建立与密码登录等价的会话。
- 所有账号类型获得正确权限。
- 强制改密状态仍拦截受保护业务操作。
- 找回密码使旧会话失效并清除临时密码状态。
- 验证码2.0关闭、开启、配置缺失、验证失败和验证成功路径均覆盖。

### 11.2 前端测试

- 密码登录和短信登录切换。
- 短信配置缺失时不显示入口。
- 获取验证码、60 秒倒计时、6 位输入限制和重新发送。
- 统一安全提示和错误提示。
- 邮箱找回保持可用。
- 验证码2.0关闭时不显示组件，开启时三个入口正确传递验证参数。
- `mustChangePassword` 登录后的导航保持正确。
- 桌面端与移动端布局可用。

### 11.3 上线验收

- API 全量测试通过。
- 管理端全量测试通过。
- 生产构建通过。
- 未配置短信时线上现有功能无回归。
- 配置短信后，三家运营商实际手机号均完成一次登录和一次找回验证。
- 服务器日志不包含验证码和密钥。
