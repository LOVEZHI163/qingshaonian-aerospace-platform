# 多赛事用户与组织账户升级设计

日期：2026-07-30
状态：待最终确认
适用系统：温州市青少年航空航天创新比赛官网、用户端、组织端、平台管理端

## 1. 背景

系统已经支持多届赛事、赛项、组别、报名、成绩和证书，但当前账户模型仍带有单赛事时期的假设：

- 登录后缺少统一的赛事入口，用户容易把“当前赛事”误解为系统唯一赛事。
- 组织是长期主体，却没有明确的“组织加入某场赛事”关系。
- `registrations.user_id` 同时表示个人报名人或组织操作账号，无法稳定表达报名归属。
- 组织账号、组织成员和赛事权限混在一起，难以保证跨赛事数据隔离。
- 部分接口依赖隐含的当前赛事，存在误读、误写其他赛事数据的风险。

本次升级采用“全局账户与组织 + 按赛事建立参与关系”的模型。赛事可以同时有 1–3 场处于公开状态，普通用户、组织负责人和平台管理员均通过明确的赛事上下文操作。

## 2. 目标

1. 普通用户登录后进入统一赛事中心，可查看所有已发布且未归档的赛事。
2. 已通过资质审核的组织可按赛事主动加入，加入后立即生效，无需平台再次审核。
3. 一个组织只能有一个组织负责人账号；一个组织负责人账号只能负责一个组织。
4. 组织负责人拥有该组织全部管理权限，不再设计组织内部的其他管理角色。
5. 普通用户可加入一个组织，但普通成员不获得组织后台管理权限。
6. 所有报名、导出、成绩与证书操作都严格按 `eventId` 隔离。
7. 同一学生在同一赛事的同一赛项只能保留一条报名；个人和组织重复提交时自动合并归属，不生成重复报名。
8. 保留平台管理员现有全部能力，并为所有赛事型页面增加统一赛事上下文。
9. 归档赛事停止新增和修改业务数据，但保留证书查询与组织历史证书下载。

## 3. 非目标

本次不设计以下功能：

- 不允许一个组织账号负责多个组织。
- 不设计组织协管员、组织管理员、赛事负责人等额外角色。
- 不设计逐场委派组织管理权限。
- 不设计组织退出、暂停或撤销赛事参与关系。
- 不要求组织为每场赛事重复提交营业执照。
- 不为普通用户建立可复用的学生档案库。
- 不新增普通用户的历史报名中心；历史访问仍以证书查询为主。
- 不改变平台管理员现有官网内容、赛事、报名、证书和用户管理能力。

## 4. 术语与角色

### 4.1 账户类型

`users.type` 继续保持三个固定类型：

| 类型 | 含义 | 可报名 | 可管理组织 | 可管理平台 |
| --- | --- | --- | --- | --- |
| `ordinary` | 普通用户 | 是 | 否 | 否 |
| `organization` | 组织负责人 | 否 | 是，仅负责自己的唯一组织 | 否 |
| `admin` | 平台管理员 | 否 | 可查看和审核全部组织 | 是 |

组织负责人账号不作为普通成员使用，也不能以个人身份报名。

### 4.2 组织成员

`memberships` 只表达普通用户与组织的关系：

- 申请由普通用户发起。
- 组织负责人审核。
- 只有 `active` 成员可在报名时关联该组织。
- 成员不获得组织后台权限。
- 组织负责人身份由 `organizations.owner_user_id` 唯一确定，不通过 `memberships.role` 授权。

成员关系的业务状态保留 `pending`、`active`、`rejected`。实现后不再接受 `owner`、`manager` 等管理角色值。

### 4.3 组织参赛关系

组织是长期主体；组织参加某场赛事时建立一条永久的 `organization_event_participations` 记录。该记录只表示“已加入”，不设置审核、暂停、退出等状态。

## 5. 总体架构

采用三层关系：

1. **全局身份层**：账户、组织、组织资质、普通成员关系。
2. **赛事参与层**：组织与具体赛事的加入关系。
3. **赛事业务层**：报名、成绩、证书，全部显式关联赛事。

平台不再根据“是否已有报名”推断组织是否参加赛事，也不复制组织和成员数据到每一届赛事。

## 6. 数据模型

### 6.1 组织负责人唯一约束

`organizations.owner_user_id` 增加唯一约束：

```sql
UNIQUE (owner_user_id)
```

服务端创建组织时同时验证：

- 账号类型必须为 `organization`。
- 账号不能已经负责其他组织。
- 组织创建后，负责人账号不能再创建第二个组织。

### 6.2 组织赛事参与表

新增：

```sql
CREATE TABLE organization_event_participations (
  organization_id TEXT NOT NULL
    REFERENCES organizations(id) ON DELETE CASCADE,
  event_id TEXT NOT NULL
    REFERENCES events(id) ON DELETE CASCADE,
  joined_by_user_id TEXT NOT NULL
    REFERENCES users(id),
  joined_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (organization_id, event_id)
);

CREATE INDEX organization_event_participations_event_id_idx
  ON organization_event_participations(event_id);
```

约束含义：

- 同一组织对同一赛事最多一条参与记录。
- 加入操作可重复调用；已有记录时返回原记录，不报重复错误。
- `joined_by_user_id` 必须是该组织当前负责人。
- 只允许加入已发布、未归档赛事。
- 组织必须处于启用状态且资质审核为通过。

### 6.3 报名归属重构

现有 `registrations.user_id` 含义不明确，升级后替换为：

```sql
created_by_user_id TEXT NOT NULL REFERENCES users(id),
personal_user_id TEXT REFERENCES users(id),
organization_id TEXT REFERENCES organizations(id),
created_via TEXT NOT NULL CHECK (created_via IN ('personal', 'organization'))
```

字段职责：

- `created_by_user_id`：首次创建这条报名的操作账号，仅用于审计。
- `personal_user_id`：能以个人身份查看该报名的普通用户，可为空。
- `organization_id`：能以组织身份管理该报名的组织，可为空。
- `created_via`：首次创建渠道。后续自动合并不会改变该值。

至少一个归属必须存在：

```sql
CHECK (personal_user_id IS NOT NULL OR organization_id IS NOT NULL)
```

报名唯一键：

```sql
UNIQUE (event_id, project_id, athlete_key)
```

`athlete_key` 由以下规范化字段精确计算：

- 姓名
- 学校
- 年级
- 手机号或家长手机号

规范化规则为：去除首尾空格、连续空白折叠、手机号去除空格和连字符；中文内容不做模糊匹配。不同赛项允许重复报名。

保留 `organization_name` 作为报名时的组织名称快照，用于历史导出；权限判断始终使用 `organization_id`。

### 6.4 证书归属

`certificates` 只以 `registration_id` 作为人员与组织归属来源。现有冗余的 `certificates.user_id` 和 `certificates.organization_id` 在本次清理测试数据后移除。

证书访问规则通过关联报名得出：

- 普通用户：`registration.personal_user_id = 当前用户`。
- 组织负责人：报名的 `organization_id` 等于其负责组织。
- 平台管理员：可访问全部。

这样个人与组织归属自动合并后，无需同步修改证书表。

### 6.5 赛事有效范围

面向用户的“当前赛事”定义为：

```text
events.status = published AND events.archived_at IS NULL
```

`events.is_current` 只用于后台默认选中或首页重点展示，不再决定用户能否看到其他并行赛事。

赛事卡片状态根据报名时间与 `registration_mode` 计算：

- 未开始
- 报名中
- 已截止

归档赛事不进入赛事中心。

## 7. 普通用户流程

### 7.1 登录入口与赛事中心

官网保留清晰的“用户登录”入口。普通用户登录后首先进入全局赛事中心，而不是直接进入某个隐含赛事。

赛事中心展示全部已发布、未归档赛事。每张卡片显示：

- 赛事名称
- 日期和地点
- 报名状态
- 用户在该赛事的报名数量
- 可执行动作：进入报名、查看当前报名、查询证书

报名未开始或已截止时仍可进入赛事详情，但不能新增报名。

### 7.2 普通用户报名

每次报名继续填写学生信息，不建立跨赛事学生档案。

用户可以：

- 不关联组织，以个人身份报名。
- 从自己的 `active` 成员关系中选择组织。

关联组织前必须额外验证该组织已经加入该赛事。若组织未加入：

- 用户仍可取消组织关联并个人报名。
- 页面明确提示“该组织尚未加入本赛事，暂不能关联组织”。

### 7.3 组织成员申请

普通用户可搜索组织并提交加入申请。组织负责人在组织后台审核。申请通过后，该用户在所有赛事中都拥有该组织的成员关系，但是否能在某场赛事关联组织，仍取决于组织是否已加入该赛事。

### 7.4 历史数据

普通用户不新增独立的历史报名页。赛事归档后：

- 报名记录不可修改。
- 已发布证书仍可通过现有证书查询入口访问和下载。

## 8. 组织负责人流程

### 8.1 登录后的组织首页

组织负责人登录后进入组织赛事中心，页面分为：

- 可加入赛事：已发布、未归档，且本组织尚未加入。
- 已加入赛事：按赛事显示报名人数、待审核数、证书数。
- 历史证书：按归档赛事只读查看和下载本组织证书。

组织资质未通过或组织被停用时，页面显示原因，不允许加入新赛事。

### 8.2 加入赛事

负责人点击“加入赛事”后，服务端在一个事务内：

1. 锁定并读取组织。
2. 验证当前账号是唯一负责人。
3. 验证组织启用且资质通过。
4. 验证赛事已发布且未归档。
5. 以 `(organization_id, event_id)` 幂等插入参与记录。
6. 写入审计日志。

成功后立即进入赛事工作台，无平台二次审核。

### 8.3 赛事工作台

加入赛事后，组织负责人拥有本组织在该赛事的完整工作能力：

- 代学生报名。
- 查看和修改本组织报名。
- 导出本组织名单。
- 查看本组织成绩。
- 查看和下载本组织证书。
- 审核普通用户加入本组织的申请。

所有页面顶部持续显示当前赛事，并提供赛事切换器。切换赛事必须重新请求数据，不能复用上一赛事的列表缓存。

归档赛事只允许查看结果与下载证书，不允许新增或修改报名。

## 9. 平台管理员流程

平台管理员保留现有全部功能：

- 概览
- 赛事及赛项、组别管理
- 官网内容、官网预览与内容发布
- 组织用户及资质审核
- 报名管理、导出与审核
- 成绩与证书管理
- 普通用户管理
- 审计、历史资源清理

升级内容仅包括：

1. 所有赛事型页面使用统一赛事切换器。
2. 页面请求显式携带 `eventId`。
3. 组织详情增加已加入赛事列表和各赛事报名、成绩、证书统计。
4. 组织资格审核仍是全局审核。

平台端不新增组织赛事加入审核、暂停、退出或逐场授权页面。

## 10. 重复报名自动合并

### 10.1 匹配条件

服务端根据 `(event_id, project_id, athlete_key)` 查找已有报名。

### 10.2 合并规则

| 已有报名 | 新提交 | 处理 |
| --- | --- | --- |
| 个人报名，无组织 | 同一学生的组织报名 | 保留同一条记录，补充 `organization_id` |
| 组织报名，无个人 | 同一学生的个人报名 | 保留同一条记录，补充 `personal_user_id` |
| 已有相同个人或相同组织 | 同一归属再次提交 | 返回已有报名，视为幂等成功 |
| 已关联其他个人用户 | 新个人用户提交 | 拒绝，不覆盖 |
| 已关联其他组织 | 新组织提交或个人试图关联其他组织 | 拒绝，不覆盖 |

合并时不得修改：

- 审核状态和驳回原因
- 成绩
- 已上传证书及发布状态
- 首次创建时间、创建渠道和创建人

合并成功后更新 `updated_at` 并记录审计日志。

### 10.3 并发处理

创建和合并必须在事务中执行：

1. 计算规范化 `athlete_key`。
2. 查询并锁定唯一键对应记录。
3. 按合并规则更新或插入。
4. 若并发插入触发唯一冲突，重新读取记录并执行一次合并判断。
5. 写入审计日志后提交。

前端不得自行判断重复报名，以服务端结果为准。

## 11. API 设计

接口命名沿用现有 `/api` 体系，所有赛事业务接口必须显式包含 `eventId`。

### 11.1 全局赛事中心

```text
GET /api/me/events
```

返回当前账户可见的已发布、未归档赛事及账户相关摘要。响应中的每项至少包括：

- `event`
- `registrationState`
- `registrationCount`
- 普通用户可关联组织及该组织是否已加入
- 组织用户的 `participationState`

### 11.2 组织加入赛事

```text
POST /api/organization/events/:eventId/join
```

组织由当前负责人账号唯一推导，客户端不提交 `organizationId`，避免越权指定其他组织。

响应：

- 首次加入：`201`
- 已加入：`200`，返回同一参与记录

### 11.3 组织赛事工作台

```text
GET /api/organization/events/:eventId/workspace
GET /api/organization/events/:eventId/registrations
POST /api/organization/events/:eventId/registrations
GET /api/organization/events/:eventId/export
GET /api/organization/events/:eventId/certificates
```

每个接口同时验证负责人、参与关系和赛事状态。归档赛事的只读接口可访问，写接口返回业务错误。

### 11.4 普通用户报名

```text
GET /api/me/events/:eventId/registrations
POST /api/me/events/:eventId/registrations
PATCH /api/me/events/:eventId/registrations/:registrationId
```

提交组织关联时，由服务端验证：

- 当前用户是该组织 `active` 成员。
- 该组织已经加入赛事。

### 11.5 平台管理接口

平台管理员使用：

```text
/api/admin/events/:eventId/...
```

任何列表、导出、统计、报名、成绩、证书写操作均不得从服务端默认赛事补全缺失的 `eventId`。缺少赛事上下文直接返回参数错误。

## 12. 权限规则

### 12.1 通用守卫

实现以下集中式权限守卫：

- `requireOrdinaryUser`
- `requireOrganizationOwner`
- `requireOrganizationEventParticipation(eventId)`
- `requireWritableEvent(eventId)`
- `requireAdmin`

### 12.2 组织数据范围

组织负责人查询或修改报名时，服务端同时限定：

```text
registration.event_id = eventId
AND registration.organization_id = 当前负责人所属组织
```

不得仅凭前端隐藏按钮或报名编号判断权限。

### 12.3 普通用户数据范围

普通用户查看或修改报名时，服务端同时限定：

```text
registration.event_id = eventId
AND registration.personal_user_id = 当前用户
```

即使报名后来合并了组织归属，个人用户仍保留访问权。

### 12.4 错误码

业务错误使用稳定代码，前端映射中文提示：

| 错误码 | 含义 |
| --- | --- |
| `EVENT_ID_REQUIRED` | 缺少赛事上下文 |
| `EVENT_NOT_AVAILABLE` | 赛事未发布或不存在 |
| `EVENT_ARCHIVED` | 赛事已归档，只允许只读操作 |
| `REGISTRATION_CLOSED` | 当前不允许报名 |
| `ORGANIZATION_NOT_APPROVED` | 组织资质尚未通过 |
| `ORGANIZATION_DISABLED` | 组织已停用 |
| `ORGANIZATION_NOT_JOINED` | 组织尚未加入该赛事 |
| `MEMBERSHIP_NOT_ACTIVE` | 当前用户不是该组织有效成员 |
| `REGISTRATION_OWNED_BY_OTHER_USER` | 报名已关联其他个人账号 |
| `REGISTRATION_OWNED_BY_OTHER_ORGANIZATION` | 报名已关联其他组织 |

错误响应不得泄露其他个人账号、手机号或组织内部信息。

## 13. 前端信息架构

### 13.1 官网

- 顶部增加明确的“用户登录”入口。
- 同时公开 1–3 场赛事时，以一场重点赛事为主，其余赛事以卡片展示。
- 登录入口不绑定某一赛事。

### 13.2 普通用户端

```text
登录
└─ 赛事中心
   └─ 赛事详情
      ├─ 报名
      ├─ 当前报名
      └─ 证书查询
```

### 13.3 组织端

```text
登录
└─ 组织赛事中心
   ├─ 可加入赛事
   ├─ 已加入赛事
   │  └─ 赛事工作台
   │     ├─ 学生报名
   │     ├─ 报名列表与导出
   │     ├─ 成绩
   │     └─ 证书
   ├─ 成员申请审核
   └─ 历史证书
```

### 13.4 路由与状态

赛事上下文使用路由参数或查询参数持久化，例如：

```text
/user/events/:eventId/registration
/organization/events/:eventId/registrations
/admin/registrations?eventId=...
```

不得只存于组件内存或依赖全局“当前赛事”。刷新页面和复制链接后必须保持同一赛事上下文。

## 14. 数据迁移与测试数据清理

当前系统尚处测试阶段，部署采用“清除测试业务数据、保留赛事配置”的策略。

### 14.1 保留

- 赛事
- 赛项
- 组别
- 官网设置
- 赛事视觉配置
- 已发布官网内容
- 系统配置

### 14.2 清除

- 测试用户与会话
- 组织、组织证件与成员关系
- 组织赛事参与关系
- 报名
- 成绩
- 证书及证书导入批次
- 对应测试上传文件
- 测试业务审计记录

### 14.3 迁移顺序

1. 生成数据库和上传目录备份。
2. 将应用置于维护状态，停止业务写入。
3. 在事务中清理测试业务数据。
4. 修改 `memberships` 角色约束。
5. 为 `organizations.owner_user_id` 增加唯一约束。
6. 创建 `organization_event_participations`。
7. 重构 `registrations` 归属字段并增加唯一约束。
8. 移除 `certificates` 冗余归属字段。
9. 禁止生产数据库为空时自动写入演示账户、组织和报名。
10. 通过标准输入一次性创建新的平台管理员，密码不得进入命令行、日志或 Git。
11. 部署 API、用户端、组织端和管理端。
12. 执行数据库完整性、接口权限和页面冒烟测试。
13. 恢复访问。

清理脚本必须先输出将删除的记录和文件数量，实际执行必须使用显式确认参数。数据库删除与物理文件清理分别记录，物理文件失败进入现有清理日志，不阻断数据库一致性。

## 15. 测试策略

### 15.1 数据约束

- 一个组织账号只能创建一个组织。
- 一个组织只能有一个负责人。
- 同一组织对同一赛事只产生一条参与记录。
- 同一学生、赛事、赛项只产生一条报名。
- 证书权限可完全通过报名归属推导。

### 15.2 组织加入

- 资质通过且组织启用时立即加入。
- 重复点击返回同一结果。
- 资质未通过、组织停用、赛事草稿或赛事归档时拒绝。
- 普通用户、其他组织账号和平台管理员不能冒充负责人调用。

### 15.3 报名合并

覆盖以下顺序：

- 个人先报、组织后报。
- 组织先报、个人后报。
- 同一归属重复提交。
- 不同个人冲突。
- 不同组织冲突。
- 两个请求并发创建。

每种情况都验证报名数量、双边可见性、状态/成绩/证书不变以及审计日志。

### 15.4 赛事隔离

为至少两场并行赛事建立同名学生、相同赛项测试数据，确认：

- 用户和组织列表不串赛事。
- 管理端导出、统计、成绩、证书不串赛事。
- 切换赛事后缓存和筛选状态正确刷新。
- 缺少 `eventId` 的管理写请求被拒绝。

### 15.5 归档行为

- 归档赛事不出现在赛事中心。
- 普通用户不能新增或修改归档赛事报名。
- 组织负责人可按归档赛事下载本组织证书。
- 普通用户仍可通过证书查询访问已发布证书。

### 15.6 回归

- 平台管理员现有所有导航和功能可用。
- 官网内容编辑、预览和发布不受影响。
- Excel 证书导入、手工录入、批量发布不受影响。
- 组织营业执照审核流程不受影响。
- 登录、退出、密码与会话安全测试通过。

## 16. 验收标准

功能完成必须同时满足：

1. 同时存在 1–3 场公开赛事时，三类账户均能明确选择赛事。
2. 已审核组织可自助、即时、幂等加入任一可用赛事。
3. 组织未加入赛事时，组织负责人不能代报，普通成员不能关联该组织。
4. 个人与组织重复报名按规则自动合并，且不丢失成绩和证书。
5. 任意请求无法读取或修改其他赛事、其他组织或其他个人的数据。
6. 组织负责人拥有唯一组织的全部组织权限，普通成员无后台管理权限。
7. 平台管理员现有功能完整保留，并能按赛事切换和管理。
8. 归档赛事停止业务写入，历史证书仍可查询或下载。
9. 清理测试业务数据后，赛事、赛项、组别和官网内容仍完整。
10. 清理后不会重新生成演示数据，并且新的平台管理员可以正常登录。
11. 自动化测试、生产构建、部署后 API 健康检查和浏览器冒烟测试全部通过。

## 17. 发布与回滚

发布前保存：

- PostgreSQL 完整备份
- 上传文件目录备份
- 当前应用镜像或发布包
- 当前环境配置快照

发布采用一次维护窗口完成数据库与应用切换，不允许旧 API 与新表结构长期混跑。

若验证失败：

1. 停止新版本容器。
2. 恢复数据库备份和上传目录。
3. 恢复上一版本应用。
4. 验证登录、赛事、报名和证书查询。

由于本次按批准方案清除测试业务数据，不执行复杂的历史报名归属猜测或兼容迁移。
