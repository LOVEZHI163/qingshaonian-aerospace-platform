# AeroGP 测试环境部署设计

## 1. 目标与范围

本轮目标是把当前项目部署到阿里云杭州 ECS，供开发者和业主进行功能测试。测试环境只使用模拟数据，不收集真实未成年人信息。

本轮包含：

- 使用 Docker Compose 统一管理前端、API 和 PostgreSQL。
- 将 API 从本地 JSON 文件改为 PostgreSQL 持久化。
- 保留本地文件卷用于测试阶段的证书上传。
- 通过服务器公网 IP 提供测试访问。
- 建立基本备份、健康检查和日志限制。

本轮不包含：

- ICP 备案、正式域名切换和受信任的 HTTPS 证书。
- 阿里云 RDS、OSS、负载均衡或多机高可用。
- 真实报名数据导入。
- 正式生产环境安全验收。

## 2. 已确认的基础条件

- ECS 地域：华东 1（杭州）。
- ECS 配置：2 vCPU、4 GiB 内存、40 GB 系统盘。
- 操作系统：Ubuntu 22.04 LTS。
- 公网 IP：`47.99.181.222`。
- 当前 ECS 是免费试用实例，试用期至 2026-10-16，不属于可备案实例。
- 域名 `aerogp.cn` 已完成企业实名认证，但当前没有 DNS 解析记录。
- 当前代码包含 React 官网、Vue 管理/报名端和 Express API。
- 当前 API 使用 `db.json` 和本地上传目录，前端仍存在 `localhost` 地址。

## 3. 方案比较与结论

### Docker Compose（采用）

优点是环境可重复、更新和迁移清晰、组件隔离，并且以后可以将 PostgreSQL 和文件存储替换为 RDS、OSS，而不改变公网入口。4 GiB 内存能够承载测试负载。

### 直接安装 Node、Nginx 和 PostgreSQL（不采用）

资源占用略低，但系统状态依赖人工配置，升级、回滚和迁移容易产生偏差。

### 宝塔面板（不采用）

提供图形界面，但会增加额外服务和公网管理入口，也不能解决当前多应用构建、数据迁移和配置一致性问题。

## 4. 目标架构

Docker Compose 管理三个服务：

1. `nginx`
   - 对外监听 80 端口。
   - `/` 提供 React 官网静态文件。
   - `/admin/` 提供 Vue 报名及管理端静态文件。
   - `/api/` 反向代理到 `api:4300`。
   - 限制请求体大小，并为静态资源配置缓存。

2. `api`
   - 运行 Express API，只在 Docker 内网监听 4300 端口。
   - 通过 `DATABASE_URL` 访问 PostgreSQL。
   - 通过挂载卷保存上传文件。
   - 提供 `/api/health` 健康检查。

3. `postgres`
   - 使用 PostgreSQL 16。
   - 只加入 Docker 内部网络，不映射宿主机 5432 端口。
   - 使用持久化卷保存数据库文件。
   - 配置健康检查，API 等数据库可用后再启动。

服务器目录统一放在 `/opt/aerogp`，包括部署文件、环境变量、上传目录和备份目录。

## 5. 数据设计与迁移

- 为用户、组织、报名、比赛、成绩和证书建立 PostgreSQL 表。
- 使用外键、唯一约束和必要索引替代 JSON 中依靠代码维护的关联。
- API 增加数据库访问层，路由不直接读写文件。
- 初次启动执行可重复的数据库迁移。
- 现有 JSON 中的演示数据作为测试种子导入；重复执行不得生成重复记录。
- 测试阶段上传文件保存在独立持久化卷，不写入容器可写层。
- PostgreSQL 数据卷和上传卷在 `docker compose down` 后仍保留。

## 6. 配置与密钥

- 生产式配置通过服务器上的 `/opt/aerogp/.env` 提供。
- `.env` 权限设为仅 root 可读，不提交到 Git。
- 数据库密码使用随机生成的高强度值。
- 前端统一使用相对地址 `/api`，官网中的报名入口改为 `/admin/`。
- Docker 日志设置单文件大小和保留数量，防止占满 40 GB 系统盘。

## 7. 测试访问与安全边界

- 测试入口暂时使用 `http://47.99.181.222`。
- 只允许模拟数据，不录入真实身份证、手机号、学校信息或证书。
- PostgreSQL 5432 和 API 4300 不对公网开放。
- 安全组保留 SSH 22 和 Web 80，删除 Ubuntu 不需要的 RDP 3389 规则。
- SSH 继续使用公钥认证，密码认证保持关闭。
- Nginx 对官网、后台和 API 统一启用 HTTP Basic Auth。使用随机生成、仅供本次测试的账号密码，凭据文件保存在服务器且仅 root 可读。
- 因为测试入口暂时是 HTTP，Basic Auth 只用于阻止随意访问，不能视为生产安全措施；测试凭据不得与任何正式账号密码复用。
- 当前应用的明文密码和客户端身份参数不满足正式上线要求。正式上线前必须改为密码哈希、服务端会话或令牌鉴权以及细粒度权限校验。

## 8. 域名迁移路径

本轮不修改 DNS。Nginx 配置预留 `aerogp.cn` 和 `www.aerogp.cn`。

正式切换时按以下顺序进行：

1. 使用满足备案条件的包年包月 ECS 完成 ICP 备案。
2. 将 `@` 和 `www` 的 A 记录指向正式服务器公网 IP。
3. 申请并部署受信任的 SSL 证书。
4. 开启 HTTPS 强制跳转和安全响应头。
5. 将测试数据清空或迁移到正式数据库。

## 9. 资源控制与备份

- 在服务器增加 2 GB swap，降低镜像构建期间内存不足风险。
- 为 API 和 PostgreSQL 设置合理的容器资源上限。
- 每天执行一次 `pg_dump`，备份到 `/opt/aerogp/backups`。
- 测试备份保留 7 天，自动删除更早的备份。
- 在部署前和数据库结构变更前额外创建一次备份。

## 10. 部署与更新流程

1. 在本机完成代码修改和自动化测试。
2. 通过 SSH 将发布内容同步到 `/opt/aerogp`。
3. 在服务器构建镜像并运行 `docker compose up -d`。
4. 等待 PostgreSQL、API 和 Nginx 健康检查通过。
5. 验证官网、后台、登录、报名、证书上传和数据持久化。
6. 更新失败时恢复上一份代码和数据库备份。

## 11. 验收标准

- `http://47.99.181.222/` 可以打开官网。
- `http://47.99.181.222/admin/` 可以打开报名及管理端。
- 前端通过同源 `/api` 正常访问 API。
- 容器重启后，数据库和上传文件仍然存在。
- 5432 和 4300 端口无法从公网访问。
- API 测试、两个前端构建和容器健康检查全部通过。
- 服务器重启后 Docker Compose 服务自动恢复。
- 数据库备份文件能够生成并通过一次恢复演练。

## 12. 后续正式上线前置条件

- 完成 ICP 备案和 HTTPS。
- 替换明文密码存储，建立可靠的服务端认证和授权。
- 收紧 CORS、上传类型和下载权限。
- 将真实文件迁移到 OSS，并评估使用 RDS。
